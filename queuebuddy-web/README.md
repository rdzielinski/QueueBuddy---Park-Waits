# QueueBuddy Web — Park Waits

A browser version of the QueueBuddy – Park Waits iOS app: a live **split-flap
departure board** of wait times for the seven Orlando theme parks (Walt Disney
World + Universal Orlando).

Phase 1: parks board → park detail → attraction history. Map and AI planner
come later.

- **Vite + React + TypeScript**, **Tailwind v4**
- **TanStack Query** for fetching + polling (board 60s, park 30s)
- **React Router** — `/` board, `/park/:parkId`, `/attraction/:attractionId`
- **Cloudflare Pages** + Pages Functions for hosting and the API layer

## Architecture — where the data comes from

The brief assumed the existing Cloudflare Worker served live park data. It
doesn't. The Worker (`../cloudflare`) is a **push + history** service:

- `POST /register` · `POST /unregister` — Live Activity push tokens
- `GET /history?name=…&since=…&limit=…` — long-form wait history from D1
- `GET /health` · `GET /debug`

Live waits come **straight from [ThemeParks.wiki](https://themeparks.wiki)** —
the same source the iOS app uses (`ThemeParksWikiClient.swift`).

So the `/api/*` layer is a thin **backend-for-frontend** built as Pages
Functions (`functions/api/`). The browser only ever calls same-origin `/api/*`
(no CORS), and the Functions fan out to the real upstreams:

```
browser ──/api/parks────────────► Function ──► ThemeParks.wiki /entity/{uuid}/live  (×7, aggregated)
        ──/api/parks/:slug/live─► Function ──► ThemeParks.wiki /entity/{uuid}/live
        ──/api/parks/:slug/schedule► Function ─► ThemeParks.wiki /entity/{uuid}/schedule
        ──/api/history?name&range► Function ──► QueueBuddy Worker /history  (D1)
```

This keeps the production Worker (serving the App Store build) untouched.

| Endpoint | Returns |
|---|---|
| `GET /api/parks` | `Park[]` — open count, avg wait, hottest ride per park |
| `GET /api/parks/:parkId/live` | `Attraction[]` — normalized live waits |
| `GET /api/parks/:parkId/schedule` | `ParkSchedule` — today's hours + Lightning Lane |
| `GET /api/history?name=…&range=24h\|7d\|30d` | `HistoryPoint[]` |

`parkId` is a slug (`magic-kingdom`, `epcot`, …). Attraction ids are
ThemeParks.wiki entity UUIDs.

### Static catalog (lands + single-rider)

Live data has no land grouping, so `src/data/catalog.json` maps each
ThemeParks.wiki UUID → `{ land, type, singleRider }`. It's generated by joining
the iOS app's `attractions.json` (id → `tpwUuid`) with the land map in
`StaticData.swift`, keyed by the UUID the live endpoint returns (no fragile
name matching). Regenerate after editing the iOS static data:

```bash
npm run build:catalog
```

## Develop

```bash
npm install

# UI-only dev (no Functions). Point /api at a deployed API for live data:
#   VITE_API_PROXY=https://your-app.pages.dev npm run dev
npm run dev

# Full stack incl. /api/* Functions (closest to production):
npm run pages:dev          # builds, then `wrangler pages dev dist`

npm run typecheck          # app + Functions
npm run build              # type-check + production build
```

## Deploy (Cloudflare Pages)

1. Push this repo to GitHub and create a **Pages** project, or use Wrangler:
   ```bash
   npm run pages:deploy
   ```
2. **Build settings** (if using the dashboard/Git integration):
   - Root directory: `queuebuddy-web`
   - Build command: `npm run build`
   - Output directory: `dist`
3. Set the **`WORKER_ORIGIN`** environment variable to your QueueBuddy Worker's
   URL (defaults to the production Worker in `wrangler.toml` /
   `functions/api/_shared.ts`):
   ```
   WORKER_ORIGIN = https://queuebuddy-push.<your-subdomain>.workers.dev
   ```
4. Confirm `/api/parks` returns live data in production.

No changes to the production Worker are required.

## Design

The signature is the split-flap board (`SplitFlap.tsx`). Digits flip with a
left-to-right ripple and snap (no flip) under `prefers-reduced-motion`. Palette
and type tokens live in `src/index.css` (`@theme`) and `src/styles/theme.css`.
Data uses tabular monospace (JetBrains Mono) so digits don't jiggle as waits
change; labels use Space Grotesk.

Wait color: ≤30 min green, ≤60 amber, >60 red, closed/down grey.
